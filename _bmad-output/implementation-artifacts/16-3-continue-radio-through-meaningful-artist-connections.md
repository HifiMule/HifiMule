# Story 16.3: Continue Radio through meaningful artist connections

Status: ready-for-dev

## Story

As a HifiMule user,
I want Radio to stay close to the current artist before moving to a clearly related artist,
so that its progression feels understandable within my curated libraries rather than drifting on genre alone.

## Acceptance Criteria

1. **Current artist first.** When the current center has eligible unheard music within the original Playback selection scope, automatic refill chooses it before any artist transition. Keep the existing five automatic upcoming target, below-two trigger, accepted manual order, source-qualified identity and one-revision append contract. A short bounded page is not proof of exhaustion.
2. **Evidence-based transition.** Only after verified current-center exhaustion, documented relationship evidence from configured-server metadata may nominate a new center: verified shared track credits with stable artist IDs or an explicit supported similar-artist response. Require stable source-qualified IDs for both artists, a candidate within the session's original selection scope, and eligible unheard music. Document and implement a deterministic evidence ranking and tie-break. The accepted transition carries its actual provider/relationship provenance and a concise truthful user-facing reason. Matching names, a shared genre, unverified metadata, and a similar-song result without a stable related artist ID cannot establish a link.
3. **Fresh-center fallback.** If no supported meaningful link yields eligible unheard music, or the first track has no unambiguous center artist, run the existing shared selector against the **original validated Playback settings snapshot**, current session exclusions and cycle heard state. Admit its first eligible result with a stable artist ID as a new center labeled “new starting point,” never as a related artist. If no such center is available, explain the waiting state without discarding the current track. Keep server-plus-track routing independent of the browsed server. Saving settings alone does not mutate an active Radio session.
4. **Cycle renewal.** If all reachable eligible tracks in the original scope have been heard in the current cycle and accepted upcoming occurrences have played or been explicitly handled, start the next cycle under the same logical Radio ID. Advance a durable cycle identity and renew heard eligibility while retaining skip and removed-suggestion exclusions, queue edits and existing occurrences. Do not renew merely because a bounded page is empty or a source/metadata request failed. Avoid immediately repeating already queued automatic tracks when another eligible choice exists.
5. **Honest waiting.** If exclusions leave no eligible music, or needed source availability is unknown, keep the accepted queue playable and enter an explained waiting state. Preserve cycle heard state on temporary failures; use bounded retry on an explicit Retry or meaningful source change, without a timer spin. Never widen configured sources, erase exclusions or query an external enrichment service.
6. **Conservative metadata.** Missing, contradictory, ambiguous, stale or genre-only artist data produces no claimed relationship. The fresh-center path remains available when the candidate scope can be evaluated. Bound relationship fetches, candidate windows, cache lifetime and work per refill independently of the audio buffers.
7. **Race-safe admission.** Center change and cycle renewal are owner mutations fenced by logical session, generation, queue revision, refill identity, expected center and cycle. Queue edit, preview, Stop and new Radio cannot let obsolete work rewrite center, cycle, explanation or queue. A settings save leaves the active snapshot unchanged; if it invalidates an in-flight evaluation, any retry still uses that snapshot. An accepted transition and its appended suggestions persist atomically; duplicate completion changes nothing.
8. **Restore.** After Quit/restart, restore the original selection context, center, cycle-level heard eligibility, durable exclusions, transition reason and queued occurrences consistently and paused. Resume continues without repeating a transition or creating a cross-session taste profile. Corrupt/unknown-version state fails safely with a recoverable explanation; pre-16.3 Radio rows without a provable original-settings snapshot must not silently adopt today's settings.
9. **Verification.** Deterministic provider fixtures on Windows, macOS and Linux cover same-artist priority, explicit links and ranking, genre-only rejection, fresh center, cycle renewal, full exclusion, temporarily unavailable sources, concurrent edits/replacement and restart. Verify each displayed explanation against its evidence. Distinguish synthetic fixture coverage from measured real-library/provider coverage and installed-package results.

**Decision details to settle in code before changing behavior:** A shared track credit with two stable artist IDs is direct relationship evidence. An explicit `similarArtist` list supports only the narrower claim that *the server suggested* a similar artist; it is not proof of a particular shared genre, collaboration or global identity. Jellyfin's Similar Artists endpoint exposes results but does not document why they are similar, so do not accept it if adapter verification cannot rule out genre-only evidence. An API returning similar songs is insufficient on its own without a stable related artist ID and substantiated relation. A relation may lead only to an artist and track eligible within the original configured source pools. Same display names on different servers are distinct identities. Same source-local track IDs on different servers are distinct tracks until 16.4 defines confident recording identity. [Source: `_bmad-output/planning-artifacts/epics.md` §Story 16.3; `_bmad-output/planning-artifacts/architecture.md` §§Playback Provider Integration, Playback Radio Selection]

**Exhaustion:** A source is verified exhausted only after its configured bounded cursor traversal completes without another eligible track; a partial page, timeout, capability error or unavailable source does not permit cycle renewal. Track source availability separately from absence and persist accepted cursor/epoch progress. A new cycle renews only heard eligibility; explicit skips and removed automatic suggestions remain indexed for the logical session. Preserve manually queued repeats and source occurrence IDs. [Source: `_bmad-output/planning-artifacts/epics.md` §Story 16.3; `_bmad-output/planning-artifacts/architecture.md` §Playback Implementation Contracts; `hifimule-daemon/src/playback/persistence.rs`]

**Original settings:** Story 16.2's refill currently reloads the mutable config file. Story 16.3 must snapshot validated settings at explicit start and use that snapshot for all active-session continuation, including after restart. Do not silently adopt a later save. If an older Radio session lacks a provable snapshot, preserve its queue/exclusions and explain that a new Radio start is needed for further automatic selection. A new explicit Radio start takes the then-current settings and a new logical ID. [Source: `hifimule-daemon/src/rpc/playback_selection.rs`; `_bmad-output/planning-artifacts/epics.md` §Story 16.3]

**Resource and privacy limits:** Keep Radio's five automatic upcoming slots, trigger below two, eight configured sources, 400 candidates per source/window, 15-second lookup and preparation deadlines, and five preparation-failure cap unless tests and measurements justify a recorded revision. These are metadata slots, not prepared audio streams. Existing compressed/PCM budgets and per-source credential handling remain intact. No server-side playlist writes or durable cross-session taste profile. [Source: `hifimule-daemon/src/playback/{radio,selection,streaming,audio}.rs`; `_bmad-output/planning-artifacts/prd.md` §§Radio and selection, Non-functional requirements]

### Latest provider API information

Current official OpenSubsonic documentation describes optional `similarArtist` entries on `getArtistInfo2` responses; the endpoint's `count` parameter bounds returned artists. Its song schema also offers optional `artists[]`, `albumArtists[]` and role-qualified `contributors[]` for direct credit evidence. Jellyfin's item DTO offers `ArtistItems[]` and `AlbumArtists[]`, though this repository currently discards some multi-artist detail. `getSimilarSongs2` returns songs from the center and similar artists but does not itself provide an unambiguous relation for every response. Jellyfin's official SDK exposes bounded `getSimilarArtists`, but does not state the relationship evidence. These are candidate adapter APIs, not a guarantee that any configured server supplies usable results; test actual responses and local artist ID resolution. Keep crate versions from this repository's lockfile and adapter compatibility tests rather than upgrading dependencies for this story. [OpenSubsonic artist info](https://opensubsonic.netlify.app/docs/endpoints/getartistinfo2/), [OpenSubsonic artist info response](https://opensubsonic.netlify.app/docs/responses/artistinfo2/), [OpenSubsonic song schema](https://opensubsonic.netlify.app/docs/responses/child/), [Jellyfin item DTO](https://typescript-sdk.jellyfin.org/interfaces/generated-client.BaseItemDto.html), [OpenSubsonic similar songs](https://opensubsonic.netlify.app/docs/endpoints/getsimilarsongs2/), [Jellyfin getSimilarArtists](https://kotlin-sdk.jellyfin.org/dokka/jellyfin-api/org.jellyfin.sdk.api.operations/-library-api/index.html)
